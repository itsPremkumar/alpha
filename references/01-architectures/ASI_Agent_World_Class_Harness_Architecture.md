# ASI-Oriented World-Class Agent Harness Architecture

## Executive design

A genuinely frontier-class computer agent should not be designed as a single autonomous prompt, a chatbot with tools, or a fixed workflow graph. The target architecture should be a **model-agnostic agent operating system**: a durable control plane that can route among frontier and open models, decompose work into specialist agents, provision isolated execution environments, interact with browsers and desktop applications, maintain long-term memory, verify outcomes, recover from failure, and continuously improve its own skills and strategies under external evaluation.

The most important architectural lesson from 2025–2026 systems is that **model intelligence and agent-system intelligence are different layers**. NVIDIA's AVO explicitly demonstrated that a surrounding harness can materially improve long-horizon performance, while NVIDIA's OpenShell work emphasizes that security authority should live below the programmable harness in the runtime. Anthropic's long-running-agent work similarly separates the brain, hands, and session state so each can fail or evolve independently. [1][2][3]

This architecture is therefore organized around six principles:

1. **Brain / hands / session separation** — reasoning, execution environments, and durable event history are independent services.
2. **Planner / executor / verifier separation** — the agent never treats “I generated it” as “the task is complete.”
3. **Capability-on-demand** — tools, skills, models, and agents are discovered and loaded dynamically rather than stuffed into every context window.
4. **Evidence-driven autonomy** — every meaningful claim of completion has observable evidence, preferably generated by deterministic tests or independent evaluators.
5. **Safe recursive improvement** — the system may evolve prompts, skills, tool wrappers, routing policies, and harness code, but promotion occurs only through isolated evaluation, security gates, regression tests, and rollback.
6. **Runtime-enforced authority** — the harness can propose actions; the security/runtime layer alone decides what actions are physically permitted.

This is an **ASI-oriented architecture**, not a claim that software architecture alone creates AGI or ASI. The intelligence ceiling still depends heavily on the underlying models, inference budget, training, and evaluation. The harness is the multiplier that turns those capabilities into a persistent, reliable agent system.

## 1. Current frontier: what the strongest systems are teaching

### NVIDIA AVO: the strongest direct lesson for your objective

NVIDIA describes AVO (Agentic Variation Operators) as a general-purpose long-horizon architecture in which the agent itself decides what to inspect, change, test, and commit, while persistent memory, execution feedback, candidate lineage, and supervision maintain the search process. NVIDIA reports a seven-day GPU-kernel optimization run with more than 500 optimization directions and reports up to 3.5% improvement over cuDNN and up to 10.5% over FlashAttention-4 on the tested configurations. NVIDIA later reported that the same general architecture reached 100.00 RHAE on the public ARC-AGI-3 set with Claude Opus 5, while noting that this is not a controlled ablation of every system component. [1][4]

**Reusable pattern:** do not use “self-improvement” as a vague reflection prompt. Treat improvement as an explicit **search process** over candidates, with lineage, measurable fitness, execution feedback, and a supervisor.

### Anthropic: long-running harness design

Anthropic's 2025–2026 engineering work highlights several important design choices: agents need durable artifacts across context windows; long-running work benefits from an initializer plus incremental worker sessions; the brain should be decoupled from execution environments; containers should be replaceable rather than precious state; and many independent “hands” should be attachable to one reasoning system. Anthropic also reports experiments with teams of parallel Claude instances working on a shared codebase and emphasizes the importance of tests that keep autonomous work aligned. [5][6][7][8]

**Reusable pattern:** make the harness **stateless where possible**, keep canonical state in a session/event store, and make compute environments disposable and re-creatable.

### OpenAI Astra: computer use plus model-level judgment and monitoring

OpenAI's September 2026 GPT-6 Astra release describes a model optimized for computer use, browsing, software engineering, science, and professional work. The published results include 72.6% on OSWorld 2.0's cited partial-score evaluation and 91.5% on BrowseComp, while the release also emphasizes agentic safeguards, auto-review, and production monitoring. OpenAI notes that Astra's written reasoning can be harder to monitor on some evaluations and treats monitorability as a continuing research priority. [9][10]

**Reusable pattern:** combine high-capability computer use with independent action monitoring rather than trusting the primary model's own explanation of why an action is safe.

### Claude Fable / Mythos: capability specialization

Anthropic's current September 2026 model line includes Claude Fable 5.1 for advanced coding and knowledge work and Claude Mythos 5.1 for more capability-intensive cybersecurity and biology research. Anthropic's model documentation also separates model capability tiers and maintains system cards for deployment decisions. [11][12]

**Reusable pattern:** your harness should not be tied to one “best model.” It should route jobs to models based on capability, cost, latency, context needs, modality, risk, and historical task performance.

### Hermes Agent: practical autonomous assistant substrate

Hermes currently combines a broad tool registry, persistent memory, scheduled tasks, skills, browser automation, delegation, plugins, multiple terminal backends, and trajectory capture. It also describes a closed learning loop involving agent-curated memory, autonomous skill creation, skill improvement during use, and cross-session recall. [13][14][15]

**Reusable pattern:** capabilities should be filesystem/package-based, installable, discoverable, and removable. The agent needs a practical substrate, not only an orchestration graph.

### OpenClaw: security and always-on operation

OpenClaw's current design emphasizes a trusted gateway, untrusted execution, deterministic policy, security auditing, per-agent sandboxing, scoped file access, network controls, credential boundaries, and explicit exposure runbooks. Its documentation is especially clear that a single gateway is not a hostile multi-tenant boundary and that materially different trust boundaries should be split across gateways, OS users, or hosts. [16][17][18]

**Reusable pattern:** “always on” should mean “durable and supervised,” not “unrestricted.”

### Alpha 2.0: integrated super-agent harness

Alpha 2.0 is a ground-up super-agent harness built around subagents, persistent memory, sandbox execution, an extensible skills/tools system, context management, and long-horizon runs. Its documentation explicitly frames the harness as a runtime environment, not merely a model wrapper or graph. [19][20][21]

**Reusable pattern:** package the hard infrastructure behind a stable runtime API so users add capabilities without rebuilding the execution engine.

## 3. Layer-by-layer architecture

### Layer 0 — Interaction surfaces

Support multiple interfaces without allowing interfaces to own agent state:

- desktop app
- web UI
- CLI/TUI
- REST/WebSocket/gRPC API
- Telegram/Discord/Slack/WhatsApp-like gateways
- voice
- file drop
- IDE integration
- scheduled triggers
- event/webhook triggers

All surfaces translate into a canonical **Task Contract**.

```yaml
TaskContract:
  task_id: uuid
  principal: user/service/agent
  goal: string
  constraints: []
  deadline: timestamp|null
  budget:
    money: number|null
    tokens: integer|null
    wall_clock_seconds: integer|null
    compute_units: number|null
  allowed_capabilities: []
  forbidden_actions: []
  risk_class: low|medium|high|critical
  success_criteria: []
  evidence_required: []
  autonomy: supervised|bounded|autonomous
  persistence: ephemeral|session|project|continuous
```

The contract becomes the immutable source of truth. Agent-generated plans may evolve, but the original goal and constraints remain anchored.

### Layer 1 — Executive / Meta-Agent

This is the top-level supervisor. It does **not** try to solve everything itself.

Its responsibilities are:

1. parse intent
2. identify missing constraints
3. estimate complexity and risk
4. choose a strategy family
5. allocate models/agents/tools
6. decompose work
7. maintain a global task state
8. detect stalls and contradictions
9. request verification
10. decide whether to retry, re-plan, delegate, or stop
11. decide whether a failure is worth learning from
12. write a final evidence-backed completion record

The Executive should have access to a small, stable set of control tools rather than hundreds of operational tools.

Recommended control tools:

```text
create_task
update_plan
spawn_agent
cancel_agent
query_run
inspect_artifact
request_verification
request_research
request_human_approval
allocate_budget
switch_strategy
checkpoint
rollback
publish_result
```

This “manager has a narrow control vocabulary” design prevents tool sprawl and keeps the high-level reasoning context clean.

### Layer 2 — Planner / Goal Compiler

Convert natural language into an explicit task graph.

Use two complementary representations:

**DAG / graph:** dependencies and parallelism.

**State machine:** retries, waiting, approvals, failures, cancellations, resumptions.

Example:

```text
GOAL
 ├── Understand
 │    ├── inspect local files
 │    ├── search authoritative sources
 │    └── identify constraints
 ├── Design
 │    ├── generate candidate plans A/B/C
 │    └── score expected value/risk/cost
 ├── Build
 │    ├── execute implementation
 │    └── run tests
 ├── Verify
 │    ├── independent critic
 │    ├── deterministic tests
 │    └── real-world smoke test
 └── Deliver
      ├── package artifacts
      ├── write evidence
      └── report limitations
```

Planning must be **receding-horizon**: do not expand the entire task tree upfront when the next steps depend on discoveries.

### Layer 3 — Strategy Engine

Before acting, choose a strategy from a library rather than inventing one every time.

Examples:

```text
DIRECT_EXECUTION
RESEARCH_THEN_EXECUTE
PLAN_PARALLEL_EXECUTE
ITERATIVE_PROTOTYPE
SEARCH_AND_VERIFY
CODE_TEST_FIX
BROWSER_TRANSACTION
DATA_ANALYSIS
MULTI_AGENT_DEBATE
EVOLUTIONARY_SEARCH
RECOVERY_MODE
```

The Strategy Engine selects a template and lets the Executive fill its parameters.

### Layer 4 — Agent Fabric

Agents should be **specialists, not identities**. Spawn them for a bounded purpose and kill them when finished.

Recommended built-ins:

```text
Researcher
SourceVerifier
Planner
Architect
Coder
CodeReviewer
Debugger
BrowserOperator
DesktopOperator
DataScientist
DatabaseAnalyst
SecurityAuditor
RedTeamer
UXDesigner
VisualCritic
DocumentEngineer
SpreadsheetEngineer
PresentationEngineer
TestEngineer
ReleaseEngineer
Observer
RecoveryAgent
EvolutionAgent
```

Use three orchestration patterns:

**Supervisor → specialists** for most tasks.

**Parallel team** when workstreams are independent.

**Debate / critique loop** only where independent disagreement can improve quality.

Subagents should have context isolation. LangChain's Deep Agents explicitly uses subagents for context quarantine, while Anthropic reports parallel agent teams for large autonomous engineering tasks. [22][7]

### Layer 5 — Model Router

Never bind the harness to one model provider.

Define a normalized model interface:

```text
reason(task, context, constraints) -> response
stream(...)
tool_call(...)
vision(...)
structured(...)
embed(...)
runtime_profile()
```

The router chooses based on:

- capability score by task family
- reliability score
- latency
- cost
- context size
- modality
- tool compatibility
- privacy requirements
- data residency requirements
- safety/risk classification
- historical benchmark performance
- current health/availability

Model selection becomes a **learning problem**. Maintain a per-model/per-task performance table and update it from evaluation outcomes.

A practical initial routing matrix:

| Work | Default | Fallback | Verification |
|---|---|---|---|
| Routine classification | fast/cheap model | local model | sampled |
| Complex planning | frontier reasoning model | second frontier model | independent critic |
| Coding | strongest coding model | second coding model | compile/tests/review |
| Browser/GUI | multimodal computer-use model | vision-capable fallback | state check |
| Research | search-capable model | second researcher | source verifier |
| Sensitive work | strongest aligned model | human | mandatory |
| Local/private | local model | approved cloud | privacy checks |

OpenAI's current Agents SDK, for example, supports agents, tools, handoffs, sessions, guardrails, MCP integration, and tracing, but your architecture should keep those ideas behind provider-agnostic interfaces rather than make your core dependent on OpenAI. [23]

## 4. Context engineering and memory

### Context is a runtime resource, not a static prompt

Anthropic's current context-engineering guidance favors just-in-time retrieval using lightweight identifiers rather than stuffing every relevant document into every context window. [24]

Implement four memory tiers:

**L0 — working context**

Current turn, active plan, current tool outputs, immediate constraints.

**L1 — episodic memory**

What happened in prior runs: successes, failures, decisions, user corrections.

**L2 — semantic memory**

Stable facts, entities, project knowledge, preferences, relationships.

**L3 — procedural memory**

Skills, workflows, tool instructions, reusable code, policies.

Store memory as typed records, not blobs of prose:

```text
MemoryRecord
- id
- type
- content
- source
- confidence
- scope
- created_at
- last_verified_at
- expiry
- provenance
- sensitivity
- embeddings/indexes
- related_tasks
- contradiction_set
```

Add a **memory falsification pass**. When new evidence conflicts with memory, do not silently overwrite it; mark a contradiction and resolve it using source quality, recency, and authority.

### Session/event store

Keep a canonical append-only event log:

```text
TaskCreated
PlanCreated
PlanRevised
AgentSpawned
ToolRequested
ToolExecuted
ToolDenied
ArtifactCreated
TestRun
VerificationPassed
VerificationFailed
HumanApproved
CheckpointCreated
RollbackExecuted
TaskCompleted
```

This lets you replay runs, debug failures, train evaluators, and recover from crashes.

## 5. Skills system

Use a filesystem/package-oriented skill format inspired by Agent Skills and Hermes.

Recommended structure:

```text

  pdf-engineering/
    SKILL.md
    references/
    scripts/
    templates/
    tests/
    evals/
  browser-research/
  windows-automation/
  github-engineering/
  database-analysis/
  video-production/
```

Each skill should contain:

```yaml
name:
description:
version:
inputs:
outputs:
required_tools:
required_permissions:
known_failure_modes:
verification:
evals:
```

Use progressive disclosure: metadata first, instructions second, references/scripts only when needed. Anthropic's current Agent Skills architecture uses this exact concept to reduce context cost while preserving rich procedural expertise. [25]

Skills should be signed/versioned packages. Never let arbitrary downloaded skill code execute with host privileges.

## 6. Tool fabric

### MCP as the capability protocol

Use MCP for tools/resources/prompts where possible. MCP defines a host/client/server architecture in which servers expose specialized capabilities while the host coordinates authorization, context, and security boundaries. Anthropic also describes MCP as a scaling mechanism for tool/data interoperability. [26][27]

### A2A for agent-to-agent interoperability

Use A2A where an external agent needs to be treated as a peer rather than a local function. Google's A2A announcement positions the protocol for cross-vendor agent collaboration with task-oriented communication. [28]

### Tool registry

Every tool should have:

```yaml
tool_id:
version:
provider:
input_schema:
output_schema:
side_effect_level:
required_permissions:
network_targets:
credential_profile:
timeout:
idempotent:
reversible:
verification_strategy:
rate_limit:
cost_estimate:
trust_level:
```

Classify every action:

```text
READ_ONLY
LOCAL_MUTATION
EXTERNAL_MUTATION
FINANCIAL
IDENTITY
SECURITY_SENSITIVE
IRREVERSIBLE
```

This classification feeds the permission engine.

## 7. Universal computer layer

To make “anything on a computer” realistic, build three layers instead of relying only on screenshots.

### Level A — semantic computer control

Use structured APIs when available:

- filesystem APIs
- application APIs
- accessibility trees
- browser DOM/Accessibility tree
- CLI/PowerShell
- IDE APIs
- OS-native automation APIs

This is faster and more reliable than pixels.

### Level B — visual interaction

Use screenshot + vision + coordinates when semantic APIs are insufficient. OpenAI's CUA and Anthropic's computer-use work demonstrate why this layer is necessary: modern work often happens through GUIs that lack standardized APIs. [29][30]

### Level C — recovery perception

After every high-impact GUI action, obtain a new observation and compare expected state vs actual state.

Example:

```text
click(button)
  -> screenshot/accessibility snapshot
  -> state matcher
  -> expected transition?
       yes -> continue
       no  -> diagnose
               -> retry
               -> alternate interaction
               -> rollback
```

Do not make “click succeeded” the success criterion. Make **state transition succeeded** the criterion.

For Windows, make the desktop layer pluggable so the same logical agent can use Windows UI Automation, browser CDP, PowerShell/CLI, WSL/Linux, or a VM-backed desktop.

## 8. Hands / execution fabric

Follow the principle: **the brain requests hands; hands are disposable**.

Execution targets should include:

```text
Local Windows process
WSL2 Linux
Docker/Podman container
MicroVM
Remote SSH host
Kubernetes pod
Cloud sandbox
GPU worker
Browser container
Remote desktop/VM
Mobile emulator/device
```

Every target implements the same interface:

```text
provision(spec) -> runtime_id
execute(runtime_id, action) -> result
observe(runtime_id) -> observation
checkpoint(runtime_id) -> checkpoint_id
restore(runtime_id, checkpoint_id)
destroy(runtime_id)
```

Anthropic's managed-agent work explicitly describes a stable `execute(name, input) -> string` style interface so brains can connect to many different hands, while NVIDIA OpenShell similarly places runtime enforcement below the agent/harness. [2][3]

## 9. Runtime security architecture

This must be a separate subsystem, not a prompt.

### Security stack

```text
Policy compiler
      ↓
Identity / principal
      ↓
Capability token
      ↓
Runtime policy
      ↓
Filesystem boundary
      ↓
Process / syscall boundary
      ↓
Network egress proxy
      ↓
Credential broker
      ↓
Audit / OCSF events
```

Use deny-by-default for autonomous or untrusted sessions.

Recommended controls:

- per-task sandbox
- per-agent identity
- least-privilege filesystem mounts
- outbound network allowlists
- DNS/SSRF controls
- endpoint-bound credentials
- no raw secret material in model context
- process isolation
- syscall restrictions where available
- resource quotas
- CPU/GPU/memory limits
- timeouts
- egress logging
- immutable audit events
- kill switch
- emergency token revocation

NVIDIA OpenShell's current architecture provides a concrete reference for this: gateway control plane, sandbox-local supervisor, filesystem/process/network isolation, policy proxy, credential handling, and structured security logging. [2][31]

OpenClaw's security guidance similarly emphasizes that the host remains the security boundary and that prompts/harness rules are not substitutes for isolation. [16][18]

### Prompt injection defense

Treat all external content as untrusted data:

```text
USER INTENT
   ↓
TASK POLICY
   ↓
AGENT
   ↓
UNTRUSTED TOOL OUTPUT ──X──> authorization
   ↓
sanitize / classify / annotate
   ↓
agent context
```

Never allow an email, webpage, repository README, document, or tool output to silently become an instruction with higher authority than the task contract.

Anthropic's Claude Code auto-mode architecture uses both input-layer prompt-injection probing and output-layer action classification. This is a useful pattern for your design, especially for autonomous computer use. [8]

## 10. Verification engine: the “truth layer”

This is one of the most important differences between a demo agent and a serious agent platform.

For every task define:

```text
Goal
→ Acceptance criteria
→ Evidence plan
→ Independent verifier
→ Completion threshold
```

Create verifier types:

```text
DeterministicVerifier
UnitTestVerifier
IntegrationVerifier
StateVerifier
VisualVerifier
SourceVerifier
SchemaVerifier
PolicyVerifier
SecurityVerifier
HumanVerifier
AdversarialVerifier
```

### Evidence matrix

```yaml
criterion: website_login_works
expected: authenticated dashboard is visible
observed:
  screenshot: artifact://...
  DOM_marker: dashboard-root
  HTTP_status: 200
  test: passed
verifier: StateVerifier
confidence: 0.99
```

The Executive should not close a task until every required criterion has a passing evidence record.

This directly addresses a recurring weakness in agent benchmarks: success often means more than producing plausible text; it requires changing an environment into the correct state. τ-bench, for example, evaluates final database state and emphasizes pass^k reliability because agents can be inconsistent across repeated runs. [32]

## 11. Self-improvement architecture

### Do not implement “recursive self-improvement” as unrestricted self-editing

Instead implement a **controlled Evolution Factory**.

```text
Production agent
      │
      ▼
Failure / success signal
      │
      ▼
Trace miner
      │
      ├── detect recurring failure
      ├── detect tool inefficiency
      ├── detect planning weakness
      ├── detect memory failure
      └── detect skill gap
      │
      ▼
Improvement hypothesis
      │
      ▼
Candidate generator
      │
      ├── prompt mutation
      ├── skill mutation
      ├── tool wrapper mutation
      ├── routing-policy mutation
      ├── memory policy mutation
      └── harness-code mutation
      │
      ▼
Isolated evaluation arena
      │
      ├── unit tests
      ├── regression tests
      ├── benchmark suite
      ├── adversarial tests
      ├── security tests
      └── cost/latency tests
      │
      ▼
Independent judge / verifier
      │
      ▼
Fitness score
      │
      ▼
Selection + promotion policy
      │
      ├── reject
      ├── archive
      ├── canary
      └── promote
```

### Candidate representation

Every self-improvement candidate gets:

```text
candidate_id
parent_version
change_type
diff
hypothesis
expected_gain
risk_delta
benchmark_set
results
regressions
security_result
cost_delta
latency_delta
confidence
promotion_status
rollback_target
```

### Fitness function

Avoid optimizing only task success.

```text
Fitness =
  quality
+ reliability
+ evidence quality
+ generalization
- cost
- latency
- security risk
- regression risk
- unnecessary tool calls
```

For example:

```text
F = 0.35 Success
  + 0.20 Reliability
  + 0.15 Evidence
  + 0.10 Generalization
  + 0.05 Speed
  + 0.05 CostEfficiency
  - 0.10 SecurityRisk
```

The weights should themselves be configurable and evaluated against real deployment goals.

### Evolutionary search

AVO is directly relevant here: it replaces fixed mutation/crossover heuristics with agentic variation driven by execution feedback. Use the same idea at several layers, but constrain the search space. [4]

Potential evolutionary dimensions:

```text
Prompt variants
Planner strategies
Tool descriptions
Tool selection policies
Context compaction strategies
Memory retrieval strategies
Subagent topologies
Model-routing policies
Verifier order
Retry policies
Skill implementations
UI interaction strategies
```

### Promotion levels

```text
L0 candidate
L1 offline benchmark
L2 adversarial benchmark
L3 shadow production
L4 canary
L5 default
```

No candidate should directly rewrite the production control plane.

## 12. Failure recovery engine

A high-end agent should assume failure.

Define failure classes:

```text
MODEL_FAILURE
TOOL_FAILURE
ENVIRONMENT_FAILURE
NETWORK_FAILURE
STATE_DRIFT
CONTEXT_LOSS
PLANNING_ERROR
USER_INTENT_AMBIGUITY
AUTH_FAILURE
POLICY_DENIAL
RESOURCE_EXHAUSTION
VERIFICATION_FAILURE
```

For each failure store:

```text
symptom
root-cause hypothesis
observed evidence
attempted recovery
result
next strategy
```

Recovery policies:

1. retry with same strategy
2. retry with altered parameters
3. refresh observation
4. restore checkpoint
5. switch model
6. switch tool
7. switch agent specialist
8. re-plan subtree
9. reduce scope
10. ask human
11. terminate safely

Implement loop detection using semantic state + tool patterns, not only repeated exact commands. Alpha 2.0 and OpenClaw both expose practical loop/sandbox/run controls that are useful references. [19][17]

## 22. End-to-end task algorithm

A canonical high-level loop should look like this:

```python
async def run_task(task_contract):
    contract = validate_contract(task_contract)
    policy = policy_engine.compile(contract)

    session = session_store.create(contract)
    runtime = None

    try:
        context = context_engine.bootstrap(contract, session)
        strategy = strategy_engine.select(contract, context)

        plan = executive.plan(contract, strategy, context)
        checkpoint = await session.checkpoint(plan)

        while not plan.is_complete():
            observation = await world.observe(contract)

            action = executive.next_action(
                contract=contract,
                plan=plan,
                observation=observation,
                memory=memory.retrieve(contract),
                policies=policy,
            )

            if action.requires_agent():
                result = await agent_fabric.dispatch(action)
            else:
                intent = action.to_tool_intent()
                authorization = policy.authorize(intent)
                result = await runtime.execute(intent, authorization)

            await session.record(result)
            context_engine.update(result)

            if result.failed:
                recovery = recovery_engine.decide(result, context)
                if recovery.is_terminal():
                    break
                plan = executive.recover(plan, recovery)
                continue

            verification = verifier_engine.check_incremental(
                contract, plan, result
            )

            if verification.requires_replan:
                plan = executive.replan(plan, verification)

            if plan.is_complete():
                final_verification = verifier_engine.verify_all(contract, session)
                if final_verification.passed:
                    return deliver_with_evidence(contract, session)

                plan = executive.replan_from_failed_verification(
                    plan, final_verification
                )

        return finalize_or_escalate(contract, session)

    finally:
        await session.flush()
        if runtime:
            await runtime.release()
```

The important property is not the exact code. It is the separation of **intent → authorization → execution → observation → verification → recovery**.

## 24. The hardest technical problems to solve

### 1. Long-horizon reliability

The main difficulty is error compounding. One bad decision early in a two-hour run can poison everything downstream.

Mitigation:

- frequent checkpoints
- incremental verification
- state re-observation
- plan revision
- independent critics
- failure-aware recovery
- durable artifacts

### 2. Context loss

Context windows remain finite and costly.

Mitigation:

- event log
- external memory
- artifact references
- progressive disclosure
- summaries with provenance
- subagent context isolation

### 3. Tool explosion

Hundreds of tools degrade selection quality.

Mitigation:

- tool namespaces
- dynamic tool discovery
- capability search
- code execution wrappers for multi-tool workflows
- risk-aware ranking

Anthropic's MCP code-execution work specifically argues that direct exposure of huge tool surfaces can consume context and that agents can scale better by writing code to call tools. [27]

### 4. False completion

Mitigation:

- evidence matrix
- independent verification
- deterministic tests
- state verification
- artifact integrity checks

### 5. Prompt injection

Mitigation:

- content classification
- instruction/data separation
- action classifiers
- capability tokens
- runtime policies
- secret isolation
- sandboxing

### 6. Self-improvement reward hacking

Mitigation:

- hidden evaluation sets
- independent evaluators
- ground-truth protection
- no evaluator access from candidate agent
- reward diversity
- behavioral audits
- rollback

This is a central finding of recent autonomous-agent-construction research: strong models can discover ways to optimize an evaluator or exploit the evaluation environment rather than improve the intended capability. [34]

## 27. Final architecture recommendation

The strongest architecture for your stated objective is a **Meta-Harness + Agent Fabric + Secure Runtime + Evolution Factory**.

The Meta-Harness is the executive brain and long-horizon coordinator.

The Agent Fabric is a dynamic pool of specialist agents and parallel teams.

The Secure Runtime is the hard authority boundary controlling filesystem, processes, network, credentials, identity, and compute.

The Evolution Factory turns failures and successes into evaluated candidate improvements.

The Knowledge Plane stores not only memories but skills, artifacts, evidence, provenance, decisions, and world state.

The Verification Plane determines whether the system actually finished the work.

The Model Router prevents the architecture from becoming obsolete when a better model appears.

The result should behave less like a chatbot and more like an **agent operating system**: it receives objectives, constructs plans, obtains capabilities dynamically, creates temporary workers, uses multiple execution environments, validates its own work, recovers when wrong, remembers what was learned, and improves only through measurable and reversible change.

That is the architecture direction most justified by the current 2026 frontier evidence. It also directly incorporates the most transferable lessons from AVO, OpenShell, Claude's long-running harness work, Astra/CUA, Hermes, OpenClaw, Alpha, MCP, A2A, and current agent evaluation research.
